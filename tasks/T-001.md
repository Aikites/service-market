# T-001 竞标大厅原型

## 1. 背景

交易网站的运营侧需要一个「竞标大厅」：需求方（人）把一句话需求挂上墙，多个 AI Agent 各自提交**方案 + 报价 + 交付周期**，由**确定性评审脚本**打分定标。整个原型不产生任何模型调用费用，评审脚本本身就是成本闸门：任何报价先过预算，再谈打分。

本任务的产物用于验证三件事：

1. 标书（本文件 front-matter）能否被脚本完整解读；
2. 报价能否被 `chain/policy.json` 的 8 元双上限硬性约束；
3. 排名能否被人工逐条复算，而不是「模型说了算」。

脚本从本文件正文的 ```json 代码块中读取唯一一个 `bidding` 对象；缺块或权重之和 ≠ 1 直接 `invalid_config`（退出码 9）。

    "required_plan_sections": ["milestones", "risks", "test_plan", "invariants"],
    "quality_rubric": {
      "milestones_at_least": 3,
      "risks_at_least": 2,
      "test_plan_at_least": 2,
      "milestones_cover_all_touched": true,

### 4.1 硬闸门（先过闸，再打分）

按顺序判定，任一不过即为**资格性废标**，不参与价格/周期归一化（避免废标拉偏基准）：

| # | 闸门 | 判据 |
|---|---|---|
| G1 | 结构完整 | 必填字段齐全，`quote_cny`、`delivery_days` 为正数 |
| G2 | 供应商锁定 | `provider` 必须等于 `policy.models.provider`（deepseek），`model` 必须在该版本价格表内 |
| G3 | 单任务上限 | `quote_cny ≤ task.budget.max_cost_cny`（8） |
| G4 | 单日上限 | `quote_cny ≤ daily_max_cny − daily_spent_cny` |
| G5 | 报价自洽 | 按 `chain/pricing.json` 复算的估算成本 ≤ `quote_cny`（禁止亏本报标） |
| G6 | 交付周期 | `delivery_days ≤ max_delivery_days`（14） |
| G7 | 路径合规 | `touched_paths` 全部命中 `allowed_paths`，且不命中 `forbidden_paths` / `policy.protected_paths` |
| G8 | 方案完整 | `plan` 含四个必填小节，且 `plan.invariants ⊆ task.invariants` |

G5 的复算口径（与 `chain/pricing.json` 完全一致，`per_1m_tokens`）：

```
est_input_cost  = input_tokens  × ((hit_ratio × cache_hit_per_1m) + ((1 − hit_ratio) × cache_miss_per_1m)) / 1e6
est_output_cost = output_tokens × output_per_1m / 1e6
est_cost_cny    = round6(est_input_cost + est_output_cost)
```

### 4.2 分项得分

| 分项 | 权重 | 算法 |
|---|---|---|
| price | 0.45 | 合格投标中最低价得 1 分，最高价得 0 分，线性插值：`(max − q) / (max − min)`；全部同价时一律 1 分 |
| delivery | 0.25 | 同上，用 `delivery_days` 归一化 |
| quality | 0.30 | 满足 `quality_rubric` 的条目加分，`得分 = 命中条数 / 条目总数` |

`total = round6(0.45×price + 0.25×delivery + 0.30×quality)`。

排序：`total` 降序 → `quote_cny` 升序 → `delivery_days` 升序 → `agent_id` 字典序升序。排名第 1 即中标；若合格投标数 < `min_bids`（2），输出 `insufficient_bids: true` 且不产生中标。

## 5. 预算与合规（严格取自 `chain/policy.json`）

| 项 | 值 | 来源 |
|---|---|---|
| 单任务上限 | 8 CNY | `budget.task.max_cost_cny` |
| 单日上限 | 8 CNY | `budget.daily.max_cost_cny` |
| 单笔熔断 | 2 CNY | `budget.circuit_breaker.single_call_max_cny` |
| 单任务调用数 | 12 | `budget.task.max_model_calls` |
| 输入/输出 token 上限 | 120000 / 30000 | `budget.task.*_tokens` |
| 供应商 | 仅 deepseek | `models.provider`、`require_single_provider` |
| 退出码 | 0/2/3/4/5/6/7/8/9 | `exit_codes` |

**任何数字都不得写在业务代码里**：`src/bid` 与 `index.html` 只能消费 `scripts/review-bids.mjs` 或 `server.js` 读出的 policy 派生值。硬编码 8 元视为验收不通过。

当日已花费一律读 `chain/state.json` 的 `global.budget.daily_spent_cny`：文件缺失记 `budget_source: "assumed_zero"`，文件为 0 字节（快照尚未写入）记 `"empty_state"`，两者均不得静默通过；非空但解析失败或与 policy 上限不一致记 `state_corrupt`（退出码 8）。

评审脚本自身不写 `chain/**`，只输出到 `reports/T-001/bid-result.json`。

## 6. 验收

```bash
node scripts/review-bids.mjs --check-task T-001   # 标书自检：字段、预算、bidding 块
node scripts/review-bids.mjs --self-test          # 内置 3 个合成投标，不读写仓库
node scripts/review-bids.mjs --task T-001 --dry-run   # 只打印，不落盘
node scripts/review-bids.mjs --task T-001            # 落盘 reports/T-001/bid-result.json
pnpm verify                                          # 十阶段总闸（含 scope / test_integrity）
```

判定标准（逐条可复核）：

1. `--check-task` 退出码 0，且输出 `task_ok: true`；
2. `--self-test` 输出中，最贵投标因 G3/G4 被废标，最低价合格投标中标；
3. 同一批投标连续跑两次，`ranking[].total` 与 `winner.agent_id` 完全一致；
4. `bid-result.json` 中每个废标项都带 `gate` 与 `reason`，不存在只有结论没有理由的条目；
5. `index.html` 打开后无控制台报错，能展示表单、投标列表、分项得分表与中标横幅；
6. `tests/bid/*.test.mjs` 断言数 ≥ 12，且无 `skip`/`todo`。

**已知风险**：

| 风险 | 影响 | 处置 |
|---|---|---|
| 权重写在本卡正文，脚本读正文而非 front-matter | 正文改动不触发 `task_sha256` 校验 | 脚本每次运行输出 `bidding_hash`，变更时人工比对 |
| 报价可能低于真实成本（G5 只挡住明显亏本） | 中标后超支 | 中标只是「入选」，实际执行仍受 `budget.circuit_breaker` 与日预算约束 |

| 投标由人手工构造，质量分易被刷 | 质量分失真 | `quality_rubric` 为离散条目，明细全量落盘，可逐条复核 |
